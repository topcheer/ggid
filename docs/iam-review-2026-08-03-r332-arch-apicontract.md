## Part 1: Architecture Consistency (Round 12)

### P0 Issues

#### P0-ARCH-01: Gateway directly connects to PostgreSQL -- breaks microservice boundary

**Files**:
- `services/gateway/cmd/main.go:144` -- `middleware.NewRBACResolver(rdb, cfg.DatabaseURL)`
- `services/gateway/cmd/main.go:151` -- `middleware.NewDBAPIKeyValidator(ctx, cfg.DatabaseURL)`
- `services/gateway/internal/router/router.go:771` -- `APIMetering(gw.cfg.DatabaseURL, ...)`
- `services/gateway/internal/router/router.go:795` -- `CheckConsent(gw.cfg.DatabaseURL, ...)`
- `services/gateway/internal/middleware/rbac_dynamic.go:285` -- `pgxpool.New(ctx, r.dbURL)`
- `services/gateway/internal/middleware/plugin_repo.go:46` -- `NewPluginRepo(pool *pgxpool.Pool)`
- `services/gateway/internal/router/integration_handlers.go:197,443,517,556,611` -- 5 additional direct DB connections

**Problem**: The gateway, which is documented as a "JWT verification + reverse proxy" service, maintains 8+ direct `pgxpool` connections to the shared PostgreSQL database. It reads from `role_route_permissions`, `api_keys`, `consent_records`, metering tables, and plugin tables directly -- bypassing identity/policy services entirely.

**Risk**:
- **Schema coupling**: Any DB migration in identity/policy breaks the gateway silently
- **RLS bypass**: Gateway's DB connections don't set tenant context (no `SET LOCAL`)
- **Data integrity**: Gateway writes to `api_keys` and metering tables outside service transaction boundaries
- **Scalability**: Each gateway replica opens its own pool, multiplying DB connections
- **Circular dependency risk**: Gateway depends on both the DB schema (owned by other services) and the services themselves (via HTTP proxy)

**Fix**: Move all DB-backed reads behind gRPC or HTTP API calls to owning services. Gateway should be stateless and protocol-only.

#### P0-ARCH-02: OpenAPI specifications are empty shells -- zero path coverage

**Files**: All 6 files in `api/openapi/v1/*/v1/*.swagger.json`
- `api/openapi/v1/audit/v1/audit.swagger.json:18` -- `"paths": {}`
- `api/openapi/v1/auth/v1/auth.swagger.json:18` -- `"paths": {}`
- `api/openapi/v1/identity/v1/identity.swagger.json:18` -- `"paths": {}`
- `api/openapi/v1/oauth/v1/oauth.swagger.json` -- `"paths": {}`
- `api/openapi/v1/org/v1/org.swagger.json` -- `"paths": {}`
- `api/openapi/v1/policy/v1/policy.swagger.json` -- `"paths": {}`

**Problem**: Every OpenAPI specification generated by `buf` has empty `paths: {}`. They only contain default `protobufAny` and `rpcStatus` definitions. The `version` field is `"version not set"` for all specs. No HTTP endpoint is documented.

**Root Cause**: `buf.gen.yaml:11-12` generates OpenAPI v2 from proto definitions, but the proto files define gRPC services without `google.api.http` annotations. Without annotations, the openapiv2 plugin cannot translate RPCs to REST paths.

**Risk**:
- No machine-readable API contract exists for the entire platform
- Console frontend and SDK consumers have no reference
- API gateway routing (60+ route prefixes in `config.go:63-136`) is undocumented
- SDK generation is impossible from current specs

**Fix**: Add `google.api.http` annotations to all proto RPC methods, or create hand-written OpenAPI specs that match the actual HTTP API surface.

#### P0-ARCH-03: Identity service gRPC port mismatch -- documentation vs implementation

**Files**:
- `services/identity/cmd/main.go:33` -- `grpcAddr = flag.String("grpc-addr", ":9090", ...)`
- `services/identity/internal/server/server.go:295` -- `net.Listen("tcp", s.cfg.GRPC.Addr)`
- Project memory (GGCODE.md): "Identity | :8081 | :50051"

**Problem**: The identity service defaults its gRPC port to `:9090` in code, but the project documentation and memory consistently reference `:50051`. Furthermore, the gateway (`config.go:63-136`) never references any identity gRPC address -- it only proxies to identity HTTP at `:8081`. No service in the codebase dials identity via gRPC.

**Risk**:
- Port `:9090` conflicts with gateway HTTP (`:8080`) range confusion and potentially MCP service
- Any deployment using documented `:50051` will silently fall back to the flag default `:9090`
- gRPC port is declared, listener started, but no consumer exists -- wasted attack surface

#### P1-ARCH-04: All gRPC ports are optional and unconnected -- declared but never dialed

**Files**:
- `services/auth/cmd/main.go:475-485` -- gRPC starts on `AUTH_GRPC_ADDR` (default `:50052`), failure is non-fatal: `"Auth gRPC: failed to listen... (continuing HTTP-only)"`
- `services/oauth/internal/server/server.go:327-330` -- gRPC starts on `OAUTH_GRPC_ADDR`, failure is non-fatal
- `services/identity/internal/server/server.go:295` -- gRPC starts unconditionally
- `services/audit/cmd/main.go:149` -- gRPC starts on `:9072`
- `services/org/cmd/main.go:105` -- gRPC starts on `:9071`
- `services/policy/cmd/main.go:102` -- gRPC starts on `:9070`

**Problem**: **Zero inter-service gRPC communication exists**. The only `grpc.Dial` reference in the entire codebase is a commented-out example in `requestid_propagation.go:38`. All service-to-service communication goes through HTTP via the gateway's reverse proxy. The gRPC servers consume memory, ports, and attack surface for no functional benefit.

**Risk**: 6 gRPC listeners (ports 50052, 9006, 9090, 9070, 9071, 9072) are exposed but serve no traffic. Each is an unmonitored attack surface.

#### P1-ARCH-05: Service discovery is hardcoded environment variables

**Files**: `services/gateway/internal/config/config.go:63-136`

**Problem**: 60+ route prefixes are mapped to backend URLs via `envOrDefault("SERVICE_URL", "http://localhost:PORT")`. There is no service registry, DNS-based discovery, or health-based routing. If a backend service moves ports, the entire routing table must be reconfigured.

**Risk**: Brittle deployment, no dynamic service discovery, no automatic failover.

- `services/auth/internal/repository/session_repo.go`
- `services/auth/internal/repository/refresh_token_repo.go`

#### P0-API-03: gRPC proto definitions don't cover the actual HTTP API surface

**Problem**: The proto files define basic CRUD operations:
- `AuthService`: Login, Register, Logout, RefreshToken, ForgotPassword, ResetPassword, ChangePassword, ListSessions, RevokeSession (9 RPCs)
- `IdentityService`: CRUD + lock/unlock + register + verify + emails (~12 RPCs)
- `AuditService`: ListEvents + GetEvent (2 RPCs)

But the actual HTTP handlers expose **hundreds** of endpoints (394 files matching `writeServiceError|writeError|WriteError`, indicating 394+ handler files with endpoints). Key missing operations in proto:
- MFA (TOTP, WebAuthn, SMS OTP, RADIUS, Yubikey)
- OAuth2/OIDC (authorize, token, introspect, revoke, device, backchannel)
- SCIM 2.0
- RBAC (roles, permissions, policies)
- Organizations, departments, teams
- Passkeys, social login, SAML
- Audit queries, SIEM forwarders, compliance reports

**Risk**: The gRPC API represents <5% of the actual API surface. Client SDKs generated from proto will be nearly useless.

#### P0-API-04: No standard error response structure across services

**Files**: Quantitative scan results:
- `writeServiceError|writeError|WriteError|writeJSONError`: 1834 matches across 394 files (using `pkg/errors`)
- `http.Error()`: 10 matches across 7 files (bypassing standard error format)
- `errors.New()|fmt.Errorf()`: 1304 matches across 239 files (raw Go errors)

**Problem**: Three error response formats coexist:
1. **Standard** (`writeServiceError` → `pkg/errors.GGIDError` → JSON with code/message/details): 1834 occurrences -- the majority
2. **Raw `http.Error`** (plain text): 10 occurrences in health/usage handlers
3. **No error handling** (raw `errors.New`/`fmt.Errorf` → likely 500 with no body): significant subset

The 7 files using `http.Error()` bypass the standard JSON error format entirely.

### P1 Issues

#### P1-API-01: Pagination is inconsistent -- cursor-based in proto, offset-based in some handlers

**Files**:
- Proto definitions: `page_token` + `page_size` (cursor-based, e.g., `ListEventsRequest.page_token`)
- Handler implementations: mixed cursor and offset patterns

**Problem**: The proto API uses `page_token` (cursor-based pagination) consistently. But the actual SQL queries in some handlers use `LIMIT/OFFSET`. The two approaches produce different consistency guarantees under concurrent writes.

---

#### P1-API-02: Field naming style mix -- snake_case vs camelCase

**Files**:
- snake_case JSON tags: 200+ files (majority, standard Go convention)
- camelCase JSON tags: 19 files (76 matches), primarily in:
  - SCIM handlers (`identity/internal/scim/handler.go:21` matches)
  - WebAuthn handlers (`auth/internal/webauthn/`)
  - OpenTelemetry/OpenAPI middleware

**Problem**: SCIM 2.0 requires camelCase per RFC 7643, while all other APIs use snake_case. This creates two JSON conventions in the same platform. While SCIM is standards-mandated, the inconsistency should be documented.

---

#### P1-API-03: No API versioning beyond `/v1/`

**Files**: `services/gateway/internal/config/config.go:63-136`

**Problem**: All routes use `/api/v1/` prefix (60+ entries). There is no `/v2/` strategy visible. No version in any header. The `Accept` header is not used for content negotiation. With proto files at `v1` and no deprecation/upgrade path defined, future API evolution will require either URL-level `/v2/` or header-based negotiation.

---

#### P1-API-04: No write-operation idempotency at the service layer

**Files**:
- `services/gateway/internal/middleware/adaptive_geo_dedup.go:173-235` -- `Idempotency-Key` header supported but **GET/HEAD only**
- `coalesce_idempotency_test.go` -- tests POST with Idempotency-Key at gateway level

**Problem**: The gateway supports `Idempotency-Key` for POST deduplication, but this is purely at the gateway coalescing layer (prevents duplicate concurrent requests). No service-level idempotency exists:
- POST `/api/v1/users` -- no idempotency key stored
- POST `/api/v1/auth/register` -- no idempotency key stored
- PUT/DELETE are naturally idempotent but not verified

**Risk**: Network retries on POST create duplicate users/resources.
